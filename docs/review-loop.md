# Action-driven peer review

Finish a reviewable action or report a problem. Prime delivers it to the configured reviewer, returns their exact-turn opinion to the writer, then delivers the writer's dispositions back. No new review starts just because a timer fired or an agent replied.

`request_review → reviewer turn → feedback → writer dispositions → reviewer receipt`

## Start locally

Build with `pnpm build`. Configure `~/.config/t3-code-mcp-prime/routes.json`:

```json
{"pair":{"writerThreadId":"WRITER_THREAD_ID","reviewerThreadId":"REVIEWER_THREAD_ID"}}
```

Use separate worktrees for independent writers. The reviewer receives a read-only instruction; Prime preserves T3 permissions and does not enforce a sandbox. Routes choose participants, not grant authority.

```sh
python3 scripts/worker-service.py start
python3 scripts/worker-service.py status
```

On macOS this installs a per-user launch agent. Elsewhere run `node dist/worker.js` under your process manager. The worker checks pending deliveries every 15 seconds, with retries backing off to five minutes. It never schedules model work without an explicit queued message or review event.

## Report an action

```sh
t3-mcp-prime request_review '{"routeId":"pair","eventId":"change-42","kind":"ready","workRef":"commit SHA; dirty diff SHA256; artifact path","summary":"Review the attached work reference against these acceptance criteria: ..."}'
```

Use `kind:"problem"` for a blocker. Include an accessible artifact and hash for uncommitted changes, including relevant untracked files. The producer owns that snapshot: `workRef` is recorded verbatim, not verified or generated by Prime. Avoid secrets in artifacts. Reusing an event ID with changed content is rejected. One active review per route keeps work from outrunning its feedback.

The reviewer returns findings in its own turn. The worker forwards up to 8,000 characters plus the exact thread/request/message references. The writer reads omitted text with `get_message`, checks the work reference against current work, and explicitly reports dispositions:

```sh
t3-mcp-prime resolve_review '{"reviewId":"REVIEW_UUID","dispositions":[{"finding":"F1","decision":"adopted","reason":"Fixed the ordering bug","evidence":"commit SHA; test command and result"}]}'
```

Submitted dispositions are immutable: identical retries are accepted, changed content requires a new work event.

Allowed decisions: `adopted`, `rejected`, `deferred`; each needs a reason and evidence or a reference explaining the deferral. For a review with no findings, report an explicit `none` finding and the validation evidence. The final receipt asks the reviewer not to initiate another review. Reading historical messages never grants permission for new work.

## Durable delivery

```sh
t3-mcp-prime queue_message '{"threadId":"THREAD_ID","requestId":"STABLE_UUID","message":"Authorized instruction"}'
t3-mcp-prime delivery_status '{}'
t3-mcp-prime deliver_pending '{"limit":3}'
```

`queue_message` persists before dispatch. It differs from the existing immediate `send_message`. Delivery to busy threads survives the caller exiting and the worker restarting. Earlier pending messages block later messages to that same thread. An unresolved message can therefore stall its recipient; other recipients continue.

The owner-only local `mailbox.sqlite` stores full pending text. After T3's projection confirms the same UUID, recipient, role and text, Prime deletes the body and retains the receipt/hash. Ambiguous HTTP outcomes retry the same UUID and text. This relies on T3's command-ID deduplication; it is not a universal exactly-once guarantee across arbitrary T3 resets. Never delete unresolved reservations or replace their IDs to retry.

Status shows delivery metadata and review phases, without bodies. `stalled:1` flags a pending message after five attempts; retries continue, and later messages to that recipient stay blocked. Inspect the recipient in T3 (archived, approval or input state) and its exact request before intervening. `delivered` means T3 recorded the user message; `closed` means T3 recorded the resolution receipt. Neither proves the task succeeded or that the reviewer agreed. Streaming/missing reviewer replies remain pending; interrupted/error replies with settled text are marked partial. Review content is not an automatic approval.

The mailbox is bound to the canonical database file identity. Desktop-managed port changes survive a restart; an explicitly configured origin stays pinned. A replaced database or changed explicit origin stops delivery rather than sending old work to a different instance. `T3_PRIME_STATE_DIR` and `T3_PRIME_ROUTES_FILE` select local state/configuration. Configure instance overrides before starting the worker; restart it to change them. Existing MCP sessions may need reconnecting to discover the new tools.

## Recover a stuck review

If the reviewer needs input/approval or finishes without usable text, inspect its exact request with `wait_for_turn` and handle the blocker in T3. To abandon that review:

```sh
t3-mcp-prime cancel_review '{"reviewId":"REVIEW_UUID","reason":"Superseded after manual inspection"}'
```

Cancellation retains text and only cancels outgoing messages that have never been attempted. It refuses while a delivery tick is active or any outgoing delivery is unresolved: let the worker reconcile the original request first. It neither interrupts a provider turn nor recalls an accepted message. A cancelled review does not forward subsequent reviewer replies. A reviewer blocked on approval/input can therefore be handled in T3 or abandoned without granting approval through Prime.

## Stop

```sh
python3 scripts/worker-service.py stop
```

This unloads the worker and removes its launch-agent registration. Pending text and receipts remain recoverable. It does not recall messages already accepted by T3. To pause delivery reliably, also stop manual `deliver_pending` calls; plain MCP registration does not start a worker.
